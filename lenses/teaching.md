# Teaching

Explains the code for someone new to it, so they learn how it works as they review.

Write this review as if for someone new to the project, or to this part of it. They should finish
it understanding both the change and the code around it.

- Explain, don't only describe. For each step, say what the code does and why it is done this way,
  and name the concept it relies on (a pattern, a library feature, a language idiom) in a few
  plain words when a newcomer might not know it.
- Give context the diff doesn't show: what the surrounding code does, where the changed function
  is called from, and what it returns to. Read the neighbouring code to get this right.
- Define project terms and abbreviations the first time they appear. Use everyday words and short
  sentences; avoid jargon you haven't explained.
- Order steps as a path through the idea, from the starting point to the result, so each step
  builds on the last. Use the `flow` diagram when seeing how the parts connect would help.
- The overview should say what problem the PR solves and the approach in terms a beginner can
  follow. Notes may run to two or three short sentences when an idea needs it.
- Comments are for things worth learning from: why an approach was chosen, what could go wrong
  and how to spot it, or a simpler way. Be encouraging and specific. Mark anything that is only
  taste as a `nit` or leave it out.
- Don't pretend to certainty: say when you're inferring how something works.
